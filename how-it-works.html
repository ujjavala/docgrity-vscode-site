How Docgrity for VS Code works

Last updated: 5 September 2026

The pipeline

  1. Collect. Docgrity gathers your repo's markdown files (**/*.md by default, excluding node_modules, build output etc., capped at 200 files). Trivial files are skipped.
  2. Pair locally. Candidate document pairs are selected with local TF-IDF cosine similarity — deterministic, instant, and free. No AI is used at this stage; code blocks are ignored so shared snippets don't cause false pairing.
  3. Assess with your model. Only the top pairs (25 by default) are sent to the language model — via VS Code's built-in vscode.lm API, meaning your own Copilot subscription or a local model. Each pair is checked for duplication and contradiction; each document is checked for open questions.
  4. Validate everything. Model responses must be valid JSON matching a strict schema — anything else is rejected, never partially trusted. Every evidence excerpt is verified verbatim against your files; findings with unverifiable evidence are dropped (hallucination guard).
  5. Show findings. Findings appear in the Docgrity activity-bar view and as diagnostics (squiggles) on the exact evidence text. Each records the model and prompt version that produced it.
  6. Act — with approval. Right-click a finding → Raise GitHub issue. Docgrity drafts a title and body (evidence, suggested next step, potential owner from git log) and shows it to you in a modal. Only after you click Create issue does it post, using VS Code's built-in GitHub sign-in, labelled docgrity / docgrity:<type>.

Potential owners

Docgrity suggests who might fix a finding by looking at the last git author of each involved file. This is always labelled potential — inferred, never asserted. It never assigns issues automatically.

Using a local model (Ollama / llama)

Docgrity talks to whatever model VS Code's language-model API exposes:

  1. Via Copilot's “Manage models”: in Copilot Chat, add your Ollama model under Manage models. It registers under the copilot vendor, so Docgrity picks it up with default settings. Optionally set docgrity.model.family to e.g. llama3.1 to force it.
  2. Via a provider extension: set docgrity.model.vendor to that provider's vendor id, or empty for any available model.

Note: the prompts demand strict JSON. Strong models handle this reliably; small local models may fail validation more often — failed responses are rejected safely, never mis-recorded.

Cost & performance

  • Pair selection is 100% local — the model is only called for the top pairs and per-doc open-question checks.
  • Caps (docgrity.maxFiles, docgrity.maxPairs) keep a scan to a bounded number of model calls.
  • Scans are cancellable; partial results are kept.

Security posture

  • Document content is treated as untrusted input: it cannot override the agent instructions, and all model output is schema-validated in code.
  • Evidence is verified verbatim against source files before a finding is recorded.
  • GitHub tokens come from VS Code's authentication API, are used only for the issue-creation request you approved, and are never logged or stored.
  • Git commands are read-only (git log, git remote get-url), executed without a shell.
  • No telemetry, no vendor servers, no data collection. See the privacy policy.

Troubleshooting

  • “No language model available” — sign in to GitHub Copilot, or configure docgrity.model.vendor/family for a local model.
  • No findings — your docs may simply agree with each other; try lowering docgrity.thresholds.*, or check the corpus caps.
  • Logs — Output panel → Docgrity channel. Use Developer: Set Log Level for more detail. Logs never contain document content or tokens.
